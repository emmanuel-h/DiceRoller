# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build debug APK
./gradlew assembleDebug

# Run unit tests (JVM, no device needed)
./gradlew test

# Run a single unit test class
./gradlew test --tests "fr.mandarine.diceroller.domain.DiceRollerTest"

# Run instrumented tests (requires connected device or emulator)
./gradlew connectedAndroidTest

# Run a single instrumented test class
./gradlew connectedAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=fr.mandarine.diceroller.DiceRollerScreenTest

# Lint
./gradlew lint
```

## Architecture

Single-module Android app (`app/`) using Jetpack Compose and MVVM.

**Layers:**

- `domain/` — pure Kotlin, no Android imports. `DieType` is the sealed supertype of anything rollable, carrying `faces` and a `label` (`"D6"`); its two implementations are `Dice` (enum of the six presets D4/D6/D8/D10/D12/D20 — the only ones with artwork) and `CustomDie` (a user-defined face count, issue #4). `DiceRoller` is stateless and takes an injectable `Random` for deterministic testing. **No two `DieType`s ever share a face count**: `CustomDie`'s `init` rejects a preset's, and `DieType.ofFaces` is the single place that resolves a bare number to a die.
- `presentation/` — ViewModel (`DiceRollerViewModel`) holds `DiceRollerUiState` as a `StateFlow`. The rule for the result is "a change to what Roll would produce clears it — except the roll itself": changing a count clears it, `clearPool` zeroes every count and clears it (a no-op on an already-empty pool, and it never touches the definitions), *adding* a custom die does not (it enters at count 0), *removing* one does only if its count was non-zero, and undoing that removal leaves it cleared. **`rollDice` empties the pool on its way out and keeps its own result**, so a roll ends a run and the next one starts from a clean selector; there is no reroll, and rolling twice in a row is a no-op. That yields the invariant **a non-null `result` implies an empty pool** — every route back to a non-empty pool runs through `incrementCount`, which clears the result. Several clearing clauses (`clearPool`'s, `removeCustomDie`'s) are therefore belt-and-braces rather than reachable; keep them, they encode the rule. Selecting a *color* never clears the result, and never touches the roll history either; neither does opening the settings sheet (`isSettingsVisible`). Selecting a *language* or a *theme* is governed by the same rule as colour — it never clears the result or the log — which the app can only guarantee because both choices stay ViewModel state (`language`/`selectLanguage`, `theme`/`selectTheme`) instead of going to the platform. Neither has a "follow the system" value: `AppLanguage` is `English`/`French` and `AppTheme` is `Light`/`Dark`, and an install that never picked starts from the device (its language if shipped, else English; its dark mode) via `data/DeviceDefaults.kt`, which both the DataStore stores (absent key → device value) and the ViewModel factory (`initialLanguage`/`initialTheme`, so the first frame is right) use. `DiceColorStore`, `AppLanguageStore`, `AppThemeStore`, `ShakeToRollStore`, `SoundStore`, `RollHistoryStore` and `CustomDiceStore` abstract persistence, each with an `InMemory…` counterpart for tests; the custom-dice store owns `normalizeCustomDice` (dedupe, sort ascending, cap at `MAX_CUSTOM_DICE` = 3). A `clock: () -> Long` is injected alongside `Random` so recorded timestamps are deterministic under test. `DiceNotation` formats a pool as `"4D6 + 1D7 + 2D8"` for history entries — the Roll button no longer repeats the pool and reads just `Roll` (issue #70), since the chip grid above it already shows the counts; `RelativeTime` formats `"3 min ago"`; `validateCustomFaces` is the pure single source of truth for what the custom-die creator will accept. Since issue #68 the last two return a **`UiText`** (a resource id plus its arguments) rather than a `String`, which is what keeps them pure Kotlin covered by fast JVM tests while their wording lives in `strings.xml`; `.resolve()` turns one into text at the display site.
- `presentation/model/` — `DiceColor`, the 12 Fantasy Dices Pack variants, each carrying a `@StringRes labelRes`, a `swatch` color, and `drawableFor(dice)`. The display name is a resource and the enum `name` is the identity: `name` is what `DataStoreDiceColorStore` persists and what artwork test tags are keyed by, so translating the label can never make a stored colour unreadable (issue #68).
- `presentation/component/` — Compose components. `DiceImage` takes a `DieType` and is **the one place that decides how a die is drawn**: a `Dice` preset renders its pack drawable with `ContentScale.Fit`, a `CustomDie` falls through to `CustomDieBadge` (a `swatch`-filled pill carrying the face count, since there is no artwork for a D7). `DiceImageSize` (enum: Compact/Inline/Small) sets the box art is fitted into and the badge's height. `DiceStepperChip` is one die type's count control, serving both kinds: the artwork *is* the control, with its left half decrementing and its right half incrementing, plus an optional `onRemove` that draws the `×` badge — presets pass null, which is the only thing making them undeletable. `AddDiceChip` and `CustomDieCreatorDialog` create a custom die. `DiceResultDisplay` shows the roll as one wrapping line of entries per die type, then a demoted total; each entry is `RolledDieImage` — the die with its rolled value drawn over its centre as an outlined white numeral, shared with the history band — plus, when several dice landed on that value, a `×N` count — which only reads as a count, not as `7 × 2`, because the value is on the die rather than between the die and the `×` (issue #69). `RollHistoryBand` is the collapsible log of past rolls. `DiceColorSwatchRow` is the 12-dot color picker. `SettingsSheet` (opened fully expanded, so the licence-required credit is never below the fold) holds **Language** (`English`/`Français`) and **Theme** (`Light`/`Dark`) as `InlineRadioGroup`s — both options side by side on one line under the section header — then a **Sound** section (one *Sound effects* switch, issue #5), then the **Shake to roll** switch and its sensitivity slider (the two switches share `SwitchRow`), then the one read-only section, the artwork's CC BY credit (`R.string.about_art_attribution`, shown there rather than in `MainActivity`). There is no About/version, app licence or contact section any more. The sheet is its own window, so it sets its bar-icon appearance from the colour scheme (`ModalBottomSheetProperties`) rather than inheriting the device's; `SettingsIconButton` (a ⚙) opens it. It was an `AboutSheet` behind an ⓘ until it gained something to *change*. `DieLabel` is the composable that names a single die on screen. `RollReveal` (`rememberRollReveal(result)`) is the roll animation (issue #1): hoisted to the screen, UI-only, it tumbles a fresh result for `ROLL_TUMBLE_MILLIS` then bounces it to rest, while `DiceResultDisplay` holds back `×N`, the total and the live region and the screen holds back the log's newest entry; it plays once per null→non-null result (saveable), and reduced motion needs no branch because Compose honours the animator duration scale. `ShakeToRollEffect` feeds the accelerometer (only while resumed) to the pure-Kotlin `ShakeDetector` and calls Roll; it is gated on `isShakeToRollEnabled` and tuned by `shakeSensitivity` (a 0–4 slider step mapped to a jolt threshold by `ShakeDetector.thresholdForSensitivity`; both persisted by `ShakeToRollStore`, default on and step 2 = 1.5g, set in the settings sheet's *Rolling* section) and off while a sheet or dialog is open. See `docs/features/roll-animation-and-shake.md`. `ClearPoolButton` is the outlined ✕ that empties the pool (issue #67). `RollSoundPlayer` (`rememberRollSoundPlayer()`) plays the roll's clatter through a `SoundPool` on the media stream (issue #5). It is triggered from `rememberRollReveal`'s `onRevealStart`, not the Roll button, so it plays once per roll and never on a rotation. `RollSound.of(result)` (pure Kotlin) picks a one-die or several-dice clip, and `isSoundEnabled` gates it (persisted by `SoundStore`, default on). See `docs/features/roll-sound.md`.
- `data/` — `DataStoreDiceColorStore` (persists by enum `name`, not ordinal), `DataStoreRollHistoryStore` (via `RollHistoryCodec`) and `DataStoreCustomDiceStore` (via `CustomDiceCodec`, just the face counts: `"3,7,100"`), plus `DataStoreAppLanguageStore`, `DataStoreAppThemeStore` (by enum `name`), `DataStoreShakeToRollStore` and `DataStoreSoundStore` (booleans, absent = on). Both codecs are hand-rolled string formats whose decoders drop corrupt entries instead of throwing. `RollHistoryCodec` keys groups **by face count, not enum name**, which is why custom dice needed no format change and why a past roll survives the user deleting the die's definition. Every store shares the one `Context.diceDataStore` delegate in `DiceDataStore.kt` — **a second `preferencesDataStore` delegate for the same file name throws at runtime**, so any new store must reuse that one.
- `MainActivity` builds the ViewModel *outside* `DiceRollerTheme` so it can pass `darkTheme = uiState.theme.isDark`, re-applying `enableEdgeToEdge(SystemBarStyle.auto { darkTheme })` when it flips so the bar icons follow the app's theme. It wraps the whole composition in **`ProvideAppLanguage`**, which supplies a `Context`/`Resources`/`Configuration`/`LayoutDirection` built for `uiState.language`. **The app never changes its own *configuration* to change language**, and that is deliberate: both platform mechanisms (`LocaleManager`, `AppCompatDelegate`) apply a locale by relaunching the activity, which was measured at 148ms of black screen, and `android:configChanges` cannot opt out of it (also measured). Localizing the composition instead makes a switch one recomposition. The costs are recorded in `docs/features/language-and-settings.md`: no `locales_config.xml`, so the app is absent from the system's per-app language screen; `Locale.getDefault()` stays on the device locale; and `bundle { language { enableSplit = false } }` is **required** — Play would otherwise ship `values-fr` as a split that an English device never installs. It owns the single screen, laid out as bands: the color swatch row (with the `SettingsIconButton` pinned at its trailing end, outside the row's own horizontal scroll), a three-row chip grid, a flexible `DiceResultDisplay`, the collapsible `RollHistoryBand`, and a pinned bottom bar holding the roll button plus, while the pool is non-empty, the `ClearPoolButton` beside it (issue #67 — hidden rather than disabled, so an empty pool leaves the bar exactly as it was and Roll spans it). `Scaffold` does not inset its `bottomBar`, so `RollBar` pads itself for the navigation bar (inside its `Surface`, so the colour runs on behind it) — without that, a three-button bar covered Roll. There is no top app bar — the title was not worth its height, which is why the ⚙ hangs off the swatch row instead: that band's height is already set by its 44dp touch targets, so the entry point costs nothing vertically (issue #66). The result and history bands share one weighted sub-column and are the only things that scroll; history is absent entirely until the first roll. The grid holds 6 presets + up to 3 custom dice + an add chip (hidden at the cap), which is **always exactly three rows** — that constant height is why the cap is 3. It costs 106dp against the ~16dp of slack issue #64 left, so at ≤680dp the result band scrolls its total into reach; every *control* still fits at 640dp, and that is the guarantee not to regress. See `docs/features/custom-dice.md` for the measured thresholds.

**Key invariant:** `DiceColor.drawableFor()` is the only place that maps `(color, die)` → drawable resource, and it takes a `Dice` — *not* a `DieType` — precisely so both its `when` branches stay compiler-enforced-exhaustive. That is why `Dice` remains an `enum` and custom dice are a separate implementation: adding a preset must stay a build error until its artwork exists. When adding a preset or a color variant, update `Dice`/`DiceColor`, add the 6 or 12 artwork files, and keep both branches exhaustive. Custom dice deliberately bypass this path entirely via `CustomDieBadge`.

**Strings:** every user-facing string — visible labels *and* `contentDescription`s — comes from `res/values/strings.xml`, with a complete `values-fr/` translation and an `en`/`fr` `res/xml/locales_config.xml` (issue #68). Counts go through `plurals`, never `if (n == 1)`. **Dice notation is not translatable text**: `die_label` (`D%1$d`), `number`, `multiplier` and `result_group_header` are `translatable="false"` and exist only so face counts are formatted arguments rather than concatenations; `DieType.label` remains the raw value for test tags, persisted keys and `poolNotation`, while the composable `dieLabel(die)` is what names a die on screen. `about_art_attribution` must end in `CC BY 4.0` in every locale — `SettingsSheet` splits that suffix off to make it the licence link. The picker's language names (`language_en`, `language_fr`) are `translatable="false"` endonyms: a language list is read by someone who does not yet read the language they are switching from. Composables call `stringResource`; the two multi-clause accessibility sentences (`DiceResultDisplay`, `RollHistoryBand`) take a `Resources` read from `LocalResources.current`, because a composable cannot look up resources inside a loop over the result's groups. Instrumented tests resolve every assertion through `androidTest/.../TestStrings.kt` so the suite passes in French too. See `docs/features/internationalization.md` and `docs/features/language-and-settings.md`.

**Artwork:** the dice art is a fixed render with numerals painted on the faces, so the rolled value needs its own contrast to sit on the die: `RolledDieImage` draws it bold white over a dark stroked outline, with no backing shape — an opaque disc was tried and hid the die (issue #69). A custom die's badge is drawn **blank** under the value (`CustomDieBadge(showFaceCount = false)`, still sized by its face count), since its face count is solid text and a `7` drawn over `1000` was unreadable; the group header and history notation still name the die. Art is CC BY 4.0 and the in-app credit line is required; see `docs/licenses/third-party-assets.md`. The roll sounds in `res/raw/` are Kenney's CC0 *Casino Audio* and need no credit.

**Theme:** `ui/theme/` is the app's own look (issue #72): parchment and ink in light mode, aged leather in dark, gold accents. **There is no dynamic colour**, and `DiceRollerTheme` has no `dynamicColor` parameter, because the wallpaper palette was what made the app look stock. Light vs dark is the user's `AppTheme`, not `isSystemInDarkTheme()` (see `docs/features/theme-and-inline-settings.md`). Every colour role is set, the `surfaceContainer*` family included, so Material-drawn surfaces (sheet, dialog, snackbar) need no overrides. Components read colours from `MaterialTheme.colorScheme`, never literals. The dice colour recolours only the art and the swatch row, never the chrome. `ParchmentBackground` draws the page as a top-lit vertical wash behind a transparent `Scaffold` (a radial vignette was tried and showed as a disc on portrait screens). The display face is **Cinzel** (OFL, two static weights in `res/font/`, since `minSdk` 24 predates variable fonts), applied via `displayStyle(base)` only to Roll, the total, the history header and the sheet/dialog titles. Do not put it in a `Typography` slot, because those slots also set die and badge numerals. See `docs/features/visual-identity.md`.

**Testing approach:**
- Unit tests (`src/test/`) test `DiceRoller`, `DiceRollerViewModel` and `DiceColor` with injected `Random` seeds for determinism. No mocking frameworks — constructor injection only. `MainDispatcherRule` swaps `Dispatchers.Main` so `viewModelScope` works off-device.
- Instrumented tests (`src/androidTest/`) use `createComposeRule()` and test the full `DiceRollerScreen` via `DiceRollerUiState` parameters or a real ViewModel with a seeded `Random`. Artwork is asserted through its content description (`"D20, amethyst"`).

## Multi-agent pipeline

New features flow through `.claude/agents/` agents orchestrated by **the-boss** (`/okay-boss <request or issue URL>`). The pipeline: boss → herald (GitHub issues) → artist (UI design) + sage (architecture) → craftsman (implementation) → inquisitor (PR review) → guardian (tests) → scribe (docs). Agent outputs land in `docs/` (features, architecture, design, testing subdirectories).
